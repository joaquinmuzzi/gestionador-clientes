# AGENTS.md

Instructions for coding agents working in Gestionador de Clientes. Humans should start with
[README.md](README.md) and [CONTRIBUTING.md](CONTRIBUTING.md); this file does not repeat them, it
records what an agent must not get wrong. [CLAUDE.md](CLAUDE.md) only points here, and the block
above is managed by Next.js (`next dev` rewrites it): leave it as it is.

## 1. Project overview

Gestionador de Clientes lets an IT support technician (software and hardware) document each
customer's infrastructure **as a map**, in the spirit of Cisco Packet Tracer but for taking notes,
not for simulating. The goal is to take out of the technician's head everything they have to
remember today: IP addresses, long passwords, configurations, backups, who does what.

The idea comes from Gabriel Natalucci, the technician who will use it. The owner and developer is
Joaquín (`joaquinmuzzi`); every change goes through a pull request.

Principles (non-negotiable):

1. **Map first.** A customer's main screen is its network diagram; double-clicking a device opens
   its sheet. Never a long list as the main view.
2. **No rigid standard.** Each device has unlimited free fields (name and multi-line value), like
   the "properties" of a draw.io shape. Basic fields are suggestions, never required.
3. **Simple.** Few screens, few clicks; nothing that looks like SAP. If a feature complicates the
   main flow, it waits.
4. **Really secure.** The app stores passwords and data of many companies; a leak is
   catastrophic. See section 7.
5. **Images are first-class.** Complex configurations (IPsec, DHCP reservations) are documented
   with screenshots attached to the device or the customer.

Implemented: login with password and TOTP, server-side sessions, login rate limiting, the
encryption helper, the user CLI, Docker Compose, the whole data model of section 5 in
`prisma/schema.prisma` (every table exists), the home page (totals, customer cards with a
thumbnail of their map, upcoming tasks, open incidents and recent activity), "Incidentes y
agenda" (`/agenda`: the tasks of the week and the incidents of every customer), the customer
pages (create, edit, delete) and the map editor on the customer page (add, move, connect, rename and delete
devices, saved automatically) and the device sheet opened with a double click (free fields,
secret fields encrypted and revealed only on request with an audit entry, roles and notes),
and attachments (images of a device, on its sheet, or of the customer, on its page; encrypted
files on disk), incidents, vulnerabilities and the agenda on the device sheet (a device with an
open incident or an overdue task is marked on the map), the end users on the customer page and
the global search in the header (`/search`, Ctrl+K; a device result opens
`/customers/<id>?device=<id>`, which centres the map on it and opens its sheet), and the
deployment on a server of its own (Tailscale or Caddy for HTTPS) with restic backups to a local
and a cloud repository and a restore test (`docs/deployment.md`, `docs/backups.md`).

## 3. Development workflow

Requirements: Node.js 22.12+ and Docker with Docker Compose (CI uses Node 22 and Postgres 18).
Install dependencies with `npm ci`; use `npm install <pkg>` only for a deliberate dependency
change.

```bash
cp .env.example .env                    # fill in the keys (see the comments)
docker compose up -d db                 # Postgres on localhost:5432
npm ci                                  # also generates the Prisma client
npm run db:migrate                      # applies (and in development creates) migrations
npm run user:create -- you@example.com  # creates the user and enrolls 2FA
npm run dev                             # app on http://localhost:3000
```

Checks, exactly what CI runs (`.github/workflows/`). Run those that your change touches, and say
which you ran:

```bash
npm run lint
npm run typecheck
npm test                                # unit tests (Vitest)
npm run build && npm run test:e2e       # end to end against the production build (port 3100)
docker compose up -d --build            # when the Dockerfile, Compose or dependencies change
```

Before changing code, read the module and its tests. When investigating a bug, reproduce it first
(a failing test, or a request against the local app), fix the cause, and run the same
reproduction again. A change that merely compiles is not verified; for UI changes, look at the
page in a browser.

## 4. Stack (confirmed by Joaquín on 2026-10-23)

- **Next.js 16 (App Router) + TypeScript + React 19**, frontend and backend in one project. The
  package is ESM (`"type": "module"`).
- **React Flow (`@xyflow/react`)** for the map: nodes with an icon per type, drag and drop,
  connections, zoom. Edges are drawn between the two devices' borders, so no handle is stored.
- **PostgreSQL 18 + Prisma 7** (`prisma-client` generator with `@prisma/adapter-pg`). The client
  is generated into `src/generated/prisma` and is not committed.
- **Tailwind CSS 4.** shadcn/ui is not initialised yet: the first change that needs more than a
  form adds it with `npx shadcn init`.
- **Own login** (no Auth.js): password + TOTP, sessions stored in the database. Auth.js with
  credentials forces JWT sessions, which cannot be revoked; this app needs short, revocable
  sessions.
- **zod 4** to validate input on the server.
- Files (screenshots) on disk or S3-compatible storage, always encrypted.
- **Docker Compose** runs everything (app, migrations, Postgres) on a self-hosted server.
- Tests: **Vitest** (unit, `test/`) and **Playwright** (end to end, `e2e/`).

If the stack changes, update this section before writing code.

### Next.js 16: what differs from earlier versions

Its documentation is in `node_modules/next/dist/docs/`. What matters most here:

- **`src/proxy.ts`** replaces `middleware.ts`. It only does an optimistic check (no session
  cookie: redirect to `/login`).
- **Cache Components is on.** Reading cookies or the session must happen inside a `<Suspense>`
  boundary, or the build fails. Pattern: the page is static and the component that reads data
  sits inside `<Suspense>`.
- **Every page, Server Action and Route Handler that touches data calls `requireUser()`**
  (`src/lib/auth/session.ts`). Layouts are not re-run on every navigation, so a check in the
  layout is not enough.
- `next start` does not work with `output: "standalone"`, so standalone output is only enabled in
  the Docker build (`BUILD_STANDALONE=1`).

## 5. Domain model

- **Customer**: a company the technician serves. It has a map, notes, contacts and end users.
- **End user**: a person at the customer. Free-form profile: technical level, what they may and
  may not touch, how to deal with them.
- **Device** (a node on the map): type (router, switch, server, PC, NAS, firewall, access point,
  printer, cloud, other), name, position on the map, icon.
  - Free fields (multi-line key and value). A field can be marked **secret**: it is stored
    encrypted and shown hidden until asked for.
  - Attachments: screenshots and images with a title.
  - Roles: who does what (free text).
  - Known vulnerabilities.
  - History of incidents and past errors (date, what happened, how it was solved).
  - Agenda: dated tasks (for example "test the backup restore").
- **Connection** (an edge on the map): between two devices, with an optional label ("IPsec VPN",
  "WAN1", "VLAN 20").
- **Customer tabs** (optional in the MVP): extra pages per customer with images and text, like
  draw.io's tabs.

MVP scope: login of one user (the technician) with 2FA; customer CRUD; a map per customer (add,
move, connect and delete devices, saved automatically); the device sheet on double click (free
fields, secrets, attachments, roles, vulnerabilities, incidents, agenda); end-user profiles;
global search (by name, IP or the text of any non-secret field); deployment with Docker Compose.

Later, not in the MVP: several technicians with per-customer permissions (today every user sees
everything), opening RDP from the app, an agent on each machine that uploads its inventory (like
msinfo32), importing draw.io diagrams, version history of passwords.

## 6. Coding conventions

- Everything in the repository is in **English**: identifiers, comments, commit messages, pull
  requests, documentation outside `docs/`, test names and command-line output. Comments explain
  *why*, not what.
- **The interface text is in Spanish (Rioplatense)**, because the person who uses the app works
  in Spanish: labels, buttons, page titles and the error messages shown in the browser.
- **Everything in `docs/` is in Spanish (Rioplatense)** too: `deployment.md`, `backups.md`,
  `user-guide.md`, `user-checklist.md` and any new document there. Commands, file names,
  environment variables and program output inside them stay as they are. They address
  "el usuario", never a named person, and the screenshots (`docs/images/user-guide/`) show only
  the made-up sample data from `prisma/seed.ts`. When a change alters what the user sees, update
  the guide and its screenshots.
- **TypeScript is strict.** ESLint (`eslint-config-next`) runs on the whole repository. There is
  no Prettier config: follow the surrounding style (double quotes, semicolons, two spaces, about
  100 columns) and do not reformat files you did not change.
- Validate every input on the server with zod. No raw SQL built with string interpolation.
- Prisma migrations are versioned: create one with `npm run db:migrate -- --name <what>` and never
  edit a migration that is already on `main`.
- Reuse before abstracting: add a helper only when two real call sites need it.
- Preserve line endings: `.gitattributes` stores text as LF. Check `git diff --stat` for
  whole-file diffs.

## 7. Security

- Secret fields and attachments are encrypted in the application (AES-256-GCM) with a master key
  from the `ENCRYPTION_KEY` environment variable, never from the repository or the database. Use
  `encrypt`/`decrypt` (or `encryptString`/`decryptString`) from `src/lib/crypto.ts`, always with a
  **context** that names where the value lives (`"<entity>:<id>:<field>"`, for example
  `"device-field:<id>:value"`). The context is authenticated data: a ciphertext copied to another
  row does not decrypt.
- Attachment files are written by `src/lib/attachments/storage.ts` only: encrypted with the
  context `"attachment:<id>:file"`, named by a random key, in `ATTACHMENTS_DIR` (the
  `attachments` volume in Docker Compose). The database cascade removes rows, not files: whoever
  deletes a customer, a device or an attachment collects the `storageKey`s in the same
  transaction and calls `removeAttachmentFiles` after it commits. Only PNG, JPG and WebP are
  accepted, recognised by their first bytes (never SVG), up to 10 MB. Images are served by the
  attachment route with `Cache-Control: no-store`, and a view leaves a `REVEAL` audit entry (one
  per user and image every 10 minutes).
- Never commit real credentials, dumps, `.env` files or customer screenshots. Sample data and
  seeds are always made up: documentation IPs (`192.0.2.x`, `198.51.100.x`, `203.0.113.x`),
  reserved domains (`example.com`, `*.test`), fake passwords.
- Login always needs a password (argon2id) and a TOTP code. There is no sign-up on the web: users
  are created with `npm run user:create`.
- Sessions live in the `Session` table (the SHA-256 of the token is stored, not the token). They
  last 8 hours at most and end after 1 hour without activity. The cookie is `__Host-session`
  (httpOnly, Secure, SameSite=Lax) in production, so the app must be served over HTTPS (or on
  localhost).
- Login rate limit: 5 failures per IP and 10 per email every 15 minutes. Every attempt is kept in
  `LoginAttempt` (login audit, 90 days). A TOTP code cannot be used twice.
- Audit log (`AuditLog`): who viewed (`REVEAL`) or changed a secret, and when; customer
  changes are logged too. Write the entry in the same transaction as the change, and never put
  a secret value in `summary`.
- The database enforces two rules with CHECK constraints and composite foreign keys (see the
  `customers_and_devices` migration): a secret `DeviceField` has an empty `value` and only an
  `encryptedValue`, and a `Connection` or `Attachment` only points to devices of its own
  customer.
- The global search (`src/lib/search/queries.ts`) filters `isSecret: false` in the query and
  never selects `encryptedValue`: a secret field is found neither by its value nor by its name.
  A new text column is added to the search only if it can never hold a secret.
- Incidents, vulnerabilities, agenda items and end users are not encrypted, so the search can
  find them; the sheet warns not to type passwords there. Their days are stored as midnight UTC
  (`fromDay`/`toDay` in `src/lib/devices/records.ts`), and whether a task is overdue is decided
  in the browser, in the technician's time zone.
- Security headers live in `next.config.ts` (no framing, nosniff, and so on).
- Backups: main server, local copy and cloud copy (restic repositories encrypted with
  `RESTIC_PASSWORD`), with a monthly restore test that decrypts every secret and attachment
  (`docs/backups.md`). A snapshot holds the database dump and the `attachments` volume and never
  `ENCRYPTION_KEY` or `RESTIC_PASSWORD`, which are kept apart. A new table or file store that
  holds encrypted data must be covered by `scripts/verify-restore.ts`. `recover` only restores
  onto an empty database.
- Security problems are reported as described in [SECURITY.md](SECURITY.md), never in a public
  issue.

## 8. Testing

- **Unit tests** use Vitest and live in `test/`, mirroring `src/` (`test/lib/auth/totp.test.ts`
  tests `src/lib/auth/totp.ts`). They import through `@/` and need no database or network.
- **End-to-end tests** use Playwright and live in `e2e/`. They run against the production build
  on port 3100 and the `DATABASE_URL` database; they create their own user
  (`e2e@example.test`) and send documentation IPs (`192.0.2.x`), so they do not touch development
  data. Customers they create are named `E2E ...` and are the only ones they delete.
- `test/docs.test.ts` checks every Markdown file: no literal escape sequences (`\n` typed as
  text) and no relative link to a missing file or heading.
- Add or update tests for every change in behaviour. When you fix a bug, write the failing test
  first.
- Never say that tests or checks passed unless you ran them, and report failures with their
  output.

## 9. UI and user experience

- The look is option D of the interface proposals ("Administrador clásico", chosen by Joaquín on
  2026-10-24): a Windows administration console. Light grey chrome (`chrome`), white panes, square
  corners (the radius tokens are redefined, so `rounded-lg` is 3px), one teal `accent`, pale blue
  `select` for what is selected, `tunnel` for VPNs and a colour per device family
  (`deviceTint` in `src/components/device-icon.tsx`). The tokens live in `src/app/globals.css`:
  use them, not raw hex values or other palettes.
- The tree on the left lives in the layout, which does not render again on navigation, so it
  fetches `/explorer` itself on every page change and when the autosave reports a change. Its
  items have the `treeitem` role, so page-level `getByRole("link")` in tests does not see them.
- Tailwind utility classes; React 19 function components. Server Components by default, client
  components only where there is interaction.
- Interface text in Spanish (section 6). Show loading and error states the way the login form
  does (`role="alert"` for errors).
- Keep it simple (principle 3): before adding a screen, check whether it fits in an existing one.

## 10. Dependencies

- Prefer the existing dependencies. A new one needs a concrete reason and a licence check.
  Runtime dependencies are pinned to exact versions in `package.json`.
- Do not edit `package-lock.json` by hand or churn it. Dependabot opens monthly, grouped version
  bumps; major versions of the framework, the database stack and the base images are done by
  hand, as planned work (see `.github/dependabot.yml`).

## 11. Git and contribution practices

- Branch from `main`. Pull requests are **squash-merged**, so the **PR title** becomes the commit
  on `main` and must follow Conventional Commits (`type(scope): imperative lowercase summary`, at
  most ~70 characters after the colon; types `feat fix docs style refactor perf test build ci
  chore revert`; scopes such as `auth`, `db`, `map`, `devices`, `customers`, `ui`, `docker`,
  `deps`). CI rejects other titles.
- Use the PR template sections (What, Why, Testing, Checklist, AI assistance). The description
  becomes the commit message on `main`.
- **AI disclosure is mandatory.** Every commit made with an AI assistant carries an
  `Assisted-by: AGENT:MODEL` trailer (for example `Assisted-by: Claude Code:claude-opus-5-5`), and
  the PR description **ends** with the same line, one line per assistant. CI (`ai disclosure`)
  fails if it is missing, malformed or not last.
- **No "Generated with Claude Code" line** (owner's request), nor any other promotional footer,
  in pull request descriptions or commits. The `Assisted-by:` line is the only AI attribution,
  and it stays last. CI rejects a description that contains such a line.
- Required CI checks: `lint`, `typecheck`, `build`, `unit tests`, `e2e tests`,
  `conventional title`, `ai disclosure`.
- One pull request per piece of work, small and focused; send a needed refactor as its own pull
  request. Add a line under *Unreleased* in [CHANGELOG.md](CHANGELOG.md) when behaviour or setup
  changes, and update README or CONTRIBUTING when they stop being true.
- Do not touch changes you did not make, and never revert someone else's work. Do not merge a
  pull request or push to `main` unless the owner asks.

## 12. Agent operating principles

1. Understand the goal and read the relevant code and its tests.
2. Identify the principles and rules above that apply (especially security, section 7).
3. Choose the smallest change that solves the problem.
4. Implement it inside the existing architecture, in the right module.
5. Add or update tests, or state why none apply.
6. Run the checks from section 3 that cover the change.
7. Read your own `git diff`: look for regressions, stray files, line-ending churn, generated
   files, secrets and unrelated edits.
8. Report what changed, what you verified (with the commands) and what remains.

Ask before irreversible or production-affecting actions and before decisions that need
information you cannot find in the repository. Do not ask about details you can determine from
the code.
